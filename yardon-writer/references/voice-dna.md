# 语言 DNA

> 全部提炼自他自己的真实文章，不是想象出来的风格。写作时优先复用这些结构。

## 一、类比公式（他最强的能力，必须保留并加强）

他写技术概念的类比有个稳定套路：**把抽象机制投到一个日常场景里，然后让场景里有个具体的检查动作。**

真实的三个例子：

- Python 类型提示 → 「超市购物车上的扫描枪，你放进去每件商品（数据），扫描枪自动检查条形码（类型），不对就滴滴报警。」
- 状态同步的老办法 → 「餐厅点菜，你跟服务员说要换一道菜，然后服务员得跑去告诉厨师、改账单、更新库存，全靠人跑来跑去，漏掉一步就出问题。」
- Prompt → 「你和 AI 之间的合同，越清晰，执行结果越好。」

规律拆出来是三步：

1. 找一个读者每天都在做、不用解释的动作（扫码、点菜）
2. 把抽象概念里的角色一一对应到场景里的角色（数据对商品，类型对条形码）
3. 让场景自带反馈（滴滴报警、漏一步就出问题）。这个反馈就是概念存在的理由

调用方法：先问「这个机制在现实里对应什么日常动作」，再问「这个动作出错时会怎样」。第二问的答案就是类比的落点。

**别写成这样**：「就像生活中的很多事情一样」「这好比一个复杂的系统」。这等于没类比。

## 二、自问自答（制造节奏转向）

真实例子：

- 「写 API 最烦的是什么？文档。」
- 「第一次看到 JSX 的人通常会有两个疑问：为什么会把 HTML 写到 JavaScript 里？这语法到底是不是合法 JavaScript？」

用法：在信息密度高的地方插一个问句，让读者停一拍，然后立刻给答案。B 模式里可以更频繁。

## 三、短句下判断（他的标志句）

真实例子：

- 「这句话是理解 React 的核心。」
- 「类型提示在这里不是装饰品，它是 FastAPI 理解你数据结构的唯一方式。」
- 「理解这一点很重要。」

用法：一段解释结束后，用一句话把重点钉住。这类句子通常十到二十字，独立成段更有力。

## 四、代码注释带经验，不带翻译

真实例子（类型字段标注）：

```
name: str           # 必填
price: float        # 必填，自动验证数字
description: Optional[str] = None  # 可选
```

真实例子（对错对照）：

```
// ❌ 不行，两个根元素
// ✅ 用 Fragment（空标签）包裹
```

规则：

- 注释写「为什么会错」「这里要注意什么」，不写「这里是定义」
- 对错对照用 ❌ 和 ✅ 标记，一眼能看出差别
- 涉及版本差异、平台限制、坑点，必须在注释里点出来

## 五、他的固定收尾（技术文保留这个签名）

每篇技术文结尾三件套：

1. 本章小结，可以用一个小表格把概念收一下
2. 下一章预告，给一个具体钩子，不写「敬请期待」
3. 签名页脚

叙事长文不用这个，但要有回环，把开头埋的东西收回来。

## 六、他的语气底色

- **克制但不冷淡。** 不用网络腔，不装热情，靠内容密度赢。
- **承认不确定。** 写「我实测是这个结果」「在我这边的环境下」，比写「通常」「一般来说」可信。
- **不居高临下。** 讲经验时用「我踩过」，不用「你应该」。
- **术语准确。** 宁可多解释一句，不用模糊词糊过去。

## 七、可以加强的三件事（他原来偏弱）

1. **第一人称经历几乎没有。** 现在的技术文里看不到作者本人。加进去，哪怕一句「我第一次写的时候也以为……」，文章立刻有温度。
2. **失败与弯路写得少。** 教程读者最想看的就是哪里会翻车。每篇至少留一处真实的坑。
3. **判断收着。** 「我建议用 A 而不是 B，因为 B 在我这个场景踩了 X」这种话，全篇至少要有一句。

## 八、实证统计出的结构特征（基于 5 篇不同系列抽样，2026-10-22 校准）

抽样范围：React、FastAPI、LangChain-RAG、AI 工程化与 MLOps、LoRA 微调、Agent 提示词。

### 1. ASCII 字符画图示

讲架构或流程时不用图片，用方框字符画：

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│   模型训练   │ ──► │   模型打包   │ ──► │   服务部署   │
└─────────────┘     └─────────────┘     └─────────────┘
```

纯文本环境里辨识度很高，是他的个人签名之一。写技术文时应主动用。

### 2. 编号章节，长文短篇不一样

长文用「一、二、三」做一级，「1.1 / 1.2」做二级。单篇指南用普通 `##`。
**规律：系列长文编号，单篇指南不编号。**

### 3. 目录 TOC 加锚点

单篇长指南开头给完整目录，带 `#锚点` 可跳转。系列文章不给，因为本身按章拆分。

### 4. 「举个例子」三行对比

讲抽象差异时，用代码块写三行对照：

```
用户："帮我写一份新能源储能电池的安全测试报告"
GPT-4：输出结构松散，缺少安全标准引用
微调后模型：严格按 IEC 62619 模板输出，每个字段精准
```

比一整段解释有效。

### 5. 加粗引导词，不是加粗内容

段落内用 `**问题**：` `**答案**：` `**示例对比**：` 这类引导词，比纯段落清晰。
注意这跟「不大量加粗」不冲突：他加粗的是**结构引导词**，不是内容里的随机强调。

### 6. 结尾标签行

单篇指南结尾带话题标签：`**标签**：#提示词工程 #AI编程 #PromptEngineering #最佳实践`

### 7. 拟人化动词

「把通用模型**驯化**成你领域的专家」，用生活化动词替代技术动词，增加记忆点。

## 九、风格一致性问题（5 篇对比后发现的）

他自己写得不统一的地方，新文章按右边规范来：

| 项 | 现状 | 应统一为 |
|---|---|---|
| 页眉冒号位置 | 有的 `**创作者**：`，有的 `**创作者：**` | `**创作者：**`，冒号在粗体内 |
| GitHub 链接 | 有一篇写成 `github.com/Yardon` | `github.com/YardonYan` |
| 页脚 emoji | 有的带 📌🏠📖🌟，有的不带 | 系列文带，单篇指南不带 |
| 自称 | 系列文用「本章」，单篇用「本文」 | 按文体区分，不要混用 |
| 开头分隔线 | 有的连写两条 `---` | 一条即可 |
