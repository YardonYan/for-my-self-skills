# 风格内核与双模式规则

## 一、冲突裁决（先看这张表，避免用错）

两套风格有几处直接矛盾，不能一句「融合」就糊过去。按文体裁决：

| 冲突点 | 学来的做法 | 他原来的做法 | 裁决 |
|---|---|---|---|
| 结构密度 | 反小标题，一口气顺下来 | 强分节，`##` `###` 加分隔线 | A 模式保留分节，B 模式弱化。技术读者要能跳着查，叙事读者要的是顺 |
| 冒号 | 全面禁用 | 大量使用，用于术语定义和代码说明 | A 模式保留，技术文不用冒号无法定义概念；B 模式叙事段禁用，改逗号或句号断开 |
| 破折号 | 禁用 | 使用 | 两模式都收敛，改逗号或直接断句，不影响可读性 |
| 双引号 | 禁用，改用「」 | 混用 | 统一用「」，代码块内的字符串不在此列 |
| 表格 | 用得少 | 大量用于概念对照 | A 模式保留，这是优势；B 模式慎用，一两张可以，多了像 PPT |
| 第一人称 | 核心，必须亲自下场 | 藏在教程后面 | 两模式都加，这是最大的提升空间 |
| 情绪表达 | 外放，用符号堆情绪 | 克制 | 适度引入，但用文字叙述情绪，不堆符号。他的调性是「代码如诗」，不用网络腔 |
| 类比 | 多，常升维到文化哲学 | 多，生活化，餐厅点菜、扫描枪 | 这是他的天赋，加强而不是替换。升维方向走工程与系统，不强求哲学 |
| 判断 | 敢说「我觉得」 | 有观点但收着 | 加强。技术文也要敢说「我建议这么选，因为踩过坑」 |

## 二、A 模式：技术长文

### 骨架（沿用他验证过的结构）

1. 一句话说清这章解决什么问题
2. 概念解释，先讲为什么需要，再讲是什么
3. 最小可运行代码
4. 逐步展开细节
5. 常见错误对照，用 ❌ 和 ✅ 并排
6. 本章小结
7. 下一章预告

### 硬规则

- **代码必须能跑。** 粘出来之前过一遍逻辑，不留伪代码当示例。
- **代码注释带判断，不是翻译。** 不写「这是初始化」，写「这里不 await 会拿到 Promise 对象」。注释是经验，不是给机器看的译文。
- **每个概念配一个生活化类比。** 这是他的强项，别省。类比要落到一个具体场景，不写「就像生活中的很多事情一样」。
- **术语第一次出现必须解释。** 一行括号补充，或者用一个类比带过。
- **对比给表格，但只对比有差异的维度。** 不把能写成一行的东西塞进表格凑行数。
- **每节结尾给一句可执行的话。** 读者读完这节，手里要有一个能立刻动手的动作。

### 允许的不规整

技术文里冒号、表格、编号列表都是合法工具。别为了追求文风统一，把可读性砍掉。

## 三、B 模式：叙事长文

### 骨架（借来的叙事弧，配他自己的素材）

1. 开头从一个具体场景或一个具体的麻烦切进去，绝不宏大叙事
2. 给出好奇心或困境，让读者想知道「然后呢」
3. 过程，带真实的失败和弯路，不是一路顺风
4. 转折点，想通的那一下
5. 结果，最好有个让人意外的点
6. 回到更大的东西，但不硬升维

### 硬规则

- **第一人称必须真实。** 写自己真做过的事。写「我当时盯着报错愣了半分钟」，不写「面对报错我进行了系统性分析」。
- **情绪用体感写，不用形容词写。** 写「手一抖把生产库的表删了」，不写「我感到非常紧张」。
- **敢下判断，姿态是承认被影响。** 写「这个说法说服了我」「我被打动了」，不写「由此可见该方案具备显著优势」。
- **先站到对方处境里，再切自己的视角。** 讲观点前把读者的处境具体化、承认它合理，然后给不同角度。读者觉得你理解他，观点才有分量。
- **扣主线句要高频。** 一次只偏离主线一点点，然后用一句短话拉回来。读者不该为了顺逻辑费脑力。
- **结尾回环。** 开头埋的意象、句子、钩子，结尾以变体回来一次。这是让文章从信息流变成作品的关键。

## 四、两模式共用的节奏规则

- **长短句交替。** 连续三句长度相近就是节奏呆板，必须打断。
- **一句话独立成段。** 全文至少三处，用来制造停顿和重量。不滥用。
- **短句下判断。** 「这句话是理解 React 的核心」这类短判断句是他文章里最好用的东西，B 模式里要更多。
- **自问自答制造转向。** 「写 API 最烦的是什么？文档。」先问再答，读者会停一拍。
- **口语转场代替小标题。** 「说到这个」「回到前面那块」「这里要多说一句」。B 模式主要靠这个推进。
- **故意的不规整。** 重复强调、中途打断、省略主语。这些不是错误，是让文字像活人说话的东西。
