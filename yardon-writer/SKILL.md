# Yardon 写作风格

> 两个来源：他自己写了五个技术系列的实战风格，加上一套成熟长文的叙事方法。这份 skill 不是缝合，是裁决之后留下能同时成立的部分。

## 一句话

把技术讲清楚，同时让人愿意读下去。硬核的内容，用活人的语气写。

## 先搞清两个来源各自贡献什么

- **他的原风格（硬实力，全保留）**：结构极清晰、代码密度高、类比生活化、术语必解释、代码注释带对错标记。
- **学来的方法论（软实力，全吸收）**：第一人称真实经历、口语节奏、敢下判断、敢写不适合谁、情绪具象化。
- **两者冲突的地方按文体裁决**，不硬融。规则见 `references/style-core.md`。

## 两种模式，动手前先选一个

### A 模式：技术长文（教程、原理、实战、踩坑记录）

读者是来查答案加学东西的。结构要清楚，代码要能跑，类比要能记住。
保留分节、表格、代码注释、本章小结。**不许为了口语化牺牲可检索性。**

### B 模式：叙事长文（项目复盘、职场观察、经验分享、观点解读）

读者是来听故事加拿观点的。结构要退到背后，人要在前面。
弱化小标题，用转场句推进；第一人称真实经历是核心；敢下判断。

**判断标准**：读者读完之后会不会去复制代码。会，就是 A；不会，就是 B。

## 使用流程

1. 吃素材，判选题。过 HKR 质检：有趣、有信息量、能共鸣，至少占两项，只占一项要重新想角度
2. 选模式（A 技术 / B 叙事）
3. 定原型（见 `references/article-prototypes.md`）
4. 开写。AI 负责背景知识、类比候选、结构建议、按角度扩写；真实经历、核心角度、情绪表达必须人来给
5. 过四层自检（见 `references/banned-and-check.md`）
6. 过阅读体验自检（见 `references/readability.md`）。这一步决定读者会不会读下去，不能跳
6. 终审定稿

## 底线

- 不许编造具体经历、数据、金额、对话。他的真实素材本身就是护城河，编一次就假。
- 技术文里术语第一次出现必须解释。
- 涉及公司业务默认脱敏：不写公司名、客户名、内部数据、服务器地址。
- 不装客观。写「我认为」「我踩过」，比写「该方案具备显著优势」可信得多。
