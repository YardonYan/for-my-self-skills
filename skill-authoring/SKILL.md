# Skill Authoring（造 Skill 的调研与提炼）

造 Skill 的难点不在写模板，在两件事：**调研够不够干净**，**提炼够不够狠**。

调研脏，后面写多漂亮都是在给错的东西排版；提炼软，产出的就是把常识换个说法。这份 Skill 只管这两件事，不管排版，也不管某个具体平台的安装。

## 何时用

- 要把一个人的公开材料整理成可调用的视角 Skill
- 要把一个主题（某个方法论、某类工程实践）整理成框架 Skill
- 要把一堆散落的项目文档、issue、复盘整理成一个能装的 Skill
- 手上已有一份 Skill，要判断它的结论值不值得信

## 何时不用

| 你的情况 | 该用 |
|---|---|
| 工作中被纠正、报错、发现知识过时，要沉淀下来 | `self-improving-agent` |
| 手上有草稿 prompt，要出几个版本挑一个 | `prompt-optimizer` |
| 要写代码，或做需求分析、方案设计、代码审查 | `dev-workflow` |
| 只是想把一份现有文档压缩改写 | 不需要 Skill，直接改 |

## 一、调研：六路并行

一个知识源至少从六个方向看。少一路就会偏：只看本人著作，得到的是他想让你看到的版本；只看外部评价，得到的是别人眼里的他。

| 路 | 找什么 | 能回答什么 | 落盘 |
|---|---|---|---|
| 1 原始论述 | 本人写的书、长文、设计文档、代码注释、RFC | 系统化的立场，反复出现的核心主张 | `01-writings.md` |
| 2 对话与即兴 | 访谈、播客、答疑、issue 里被追问时的回复 | 被追问时怎么反应、哪里改过口 | `02-conversations.md` |
| 3 措辞与表达 | 短文本、术语、他自己造的词、类比习惯 | 可复用的表达规则，而不是语气模仿 | `03-expression.md` |
| 4 外部评价 | 同行批评、对比、事后复盘、失败案例 | 盲区在哪，什么问题这个视角帮不了 | `04-external-views.md` |
| 5 决策与行为 | 实际选择、取舍记录、承诺兑现情况 | 说的和做的差多少 | `05-decisions.md` |
| 6 时间线与近期 | 关键转折点、最近 12 个月的动态 | 防过时，标清信息截止点 | `06-timeline.md` |

四条硬规则：

1. **每条都要落盘。** 不写进文件的调研等于没做，下一个会话也接不上。
2. **每条标来源类型。** 一手（本人写的/本人做的）、二手（别人转述）、推断（你根据材料得出的）分三档，不许混。推断当结论写，是最常见的塌方点。
3. **矛盾保留。** 材料里两处说法不一致，原样记下来并在提炼时收进「内在张力」。抹平矛盾等于扔掉最有信息量的部分。
4. **调研文件放在 Skill 目录里。** 复制整个目录就能独立使用，不依赖任何外部路径。

### 信源权重

不设绝对的行业黑名单，按可追溯性排权重：

| 层级 | 来源 | 权重 |
|---|---|---|
| 一手 | 本人著作、原始文档、代码、决策记录、长访谈全文 | 最高 |
| 一手 | 机构官方文档、官方发布说明、规范原文 | 最高 |
| 二手 | 权威媒体深度报道、同行评审、有署名的技术分析 | 中 |
| 二手 | 洗稿站、聚合号、无出处的转载、百科条目 | 低，仅作线索 |
| 推断 | 你从上述材料推导出的结论 | 必须标注，不单独成立 |

中文场景优先找原始视频（B 站原片，非搬运）、播客原音频（小宇宙）、行业媒体原文（36 氪、晚点、财新、极客公园、机器之心）。公众号与知乎内容只在能追到原始出处时使用，引的时候引原始出处。

## 二、提炼：三重验证

调研完会有一堆候选论点，通常 15 到 30 条。逐条过三关，**三关全过才算核心模型**。

| 关 | 问题 | 过关标准 |
|---|---|---|
| 跨域复现 | 这个观点在两个以上不相关的场景里都出现过吗 | 只在一个话题里说过，属局部看法，不算模型 |
| 生成力 | 拿它去推此人对全新问题的立场，推得动吗 | 只能复述原场景 = 没有生成力 |
| 排他性 | 换个聪明人会不会也这么说 | 会 = 常识，不是洞察 |

判定与去向：

| 过关数 | 去向 | 数量 |
|---|---|---|
| 3 / 3 | 核心模型，每条带来源证据和失效条件 | 3 到 7 个 |
| 1 到 2 | 降为单条启发式（如果 X 则 Y，附案例） | 5 到 10 条 |
| 0 | 丢弃 | — |

铁律：**宁少勿多。** 3 个有证据的模型，强于 10 条正确但没信息量的原则。宁可写 3 个，不要为了凑数把常识塞进去。

## 三、写进 SKILL.md：让它扛得住

调研和提炼做得再好，写出来扛不住三件事就白费：环境不支持、上下文不够、以及自己骗自己。

### 3.1 失败降级表

用三列写，一行一个已知会挂的场景。第一列是触发条件，第二列是一线修复，第三列是还不行时的兜底。

| 触发条件 | 一线修复 | 仍失败兜底 |
|---|---|---|
| 运行环境不支持并行子代理 | 降级串行，做完一个落盘一个，禁止挂起等待 | 单代理分多轮，每轮只做一个维度并立即落盘 |
| 上下文窗口不够，跑到中途爆掉 | 每个阶段结束把状态写盘，新会话从文件恢复 | 分三段会话，每段开头先读已落盘的文件 |
| 成本超出用户预期 | 开跑前报量级，让用户选档 | 用户中途喊停，已落盘内容即中间产物，续跑不清零 |
| 单路调研超时，搜不到有效内容 | 不等，继续推进，在提炼时标「信息不足」 | 在诚实边界里写明该维度薄弱 |
| 检索工具不可用 | 换运行环境里等价的工具 | 转纯本地材料模式，引导用户提供素材 |
| 材料数量太少（可用来源不足 10 条） | 开跑前就告知，核心模型减到 2 到 3 个 | 加大诚实边界篇幅，标注推测成分 |
| 多路结论互相冲突 | 保留矛盾，不调和 | 单列「内在张力」小节收录 |
| 写作规范与宿主平台冲突（触发词超长、路径写死） | 按宿主平台改，不按上游原文照抄 | 在 README 写明该 Skill 适配的目录约定 |

写完这张表要能回答一个问题：**第一次跑，最可能挂在哪一行？** 挂过的位置必须有一行对应。没有对应行的表是抄来的模板，不是经验。

### 3.2 检查点

只在三处停：调研完成、提炼完成、验收完成。每个检查点只问一件事，并且**不阻塞不依赖它的产出**。

- 调研完成：各路的来源数量和关键发现，有没有哪路是空的
- 提炼完成：模型几个、启发式几条、张力几对，方向对不对
- 验收完成：三项测试结果，不过的话薄弱在哪

检查点是让用户纠偏，不是扣住交付。能给默认值就给默认值。

### 3.3 诚实边界

至少 3 条，而且要具体到能让人判断「这个场景我该不该用」。

| 弱写法（等于没写） | 强写法（能指导决策） |
|---|---|
| 本 Skill 仅供参考，不能替代专业判断 | 材料截止 2026-03，此后的政策变化不在覆盖范围内 |
| 模型可能出错 | 此视角在平台经济与网络效应问题上结构性看不见，分析这类问题需补另一个视角 |
| 不保证准确 | 原始记录在这类场景缺失，第 4 条模型为推断，置信度低于其余三条 |

弱写法是免责声明，强写法是使用说明。写到能让人说「那我这个问题不该用它」，才合格。

### 3.4 自检要能验证

这是最容易糊弄的一节，也是上游项目翻车的地方：**用关键词统计冒充质量门**。

| 不算检查 | 算检查 |
|---|---|
| 全文出现过「局限」两个字 | 每条模型都写了失效条件，能逐条指出来 |
| 正则数出 6 个列表项 | 随机抽 3 条结论回原文核对，3/3 命中 |
| 有「诚实边界」这个标题 | 边界里有具体场景，不是免责套话 |
| 文件里写了「5 个模型」 | 用脚本数实际标题数量，和声明一致 |

规则一句话：**能被一个 grep 满足的检查，不算检查。** 检查项必须能产出「过/不过」的事实依据，而不是词频。

验收至少跑这三项：

1. 已知题：选 3 个源材料里明确有立场的问题，带着新 Skill 回答，对照原文看方向是否一致
2. 边缘题：选 1 个源材料没谈过但相关的问题，期望输出「基于 X 和 Y 推断，可能……但不确定」，斩钉截铁就是失败
3. 风格题：写 100 字，判断是不是通用助手腔；是就回去改表达规则

迭代上限 2 轮。两轮还不过，把薄弱项写进诚实边界交付，不要无限打磨。

## 四、评估一份现成 Skill

拿到别人的 Skill，按六问过一遍，每问都有判定依据：

| 问 | 怎么看 | 不合格信号 |
|---|---|---|
| 信息密度 | 行数 vs 可执行信息量。500 行里 300 行是宣传和自我夸奖 | 大量篇幅在讲它多好 |
| 失败降级 | 有没有 if-then 降级表，覆盖的是真实场景还是套话 | 只写「如遇问题请重试」 |
| 结论可溯源 | 每条结论能不能指到具体来源 | 引用含糊，或引用自己 |
| 自检可信度 | 自检是关键词统计还是真验证 | 靠正则数条目、按词频判分 |
| 可移植性 | 路径是变量还是写死某一端的目录 | 满篇硬编码，换平台就落错位置 |
| 合规 | 有没有教你去拿不该拿的东西（盗版源、未授权数据）；处理真人材料时有无同意与边界 | 出现影子图书馆、默认放行公众人物 |

前五条决定它好不好用，第六条决定它能不能进公共库。**合规不过，能力再强也不收。**

## 五、反模式

| # | 不做 | 为什么 |
|---|---|---|
| 1 | 编造原话和数据 | 查不到出处就不写，宁可缺一条 |
| 2 | 把常识包装成独特洞察 | 过不了排他性那一关，读者一眼看穿 |
| 3 | 只收正面材料，忽略批评 | 粉丝滤镜，产出的视角没有盲区反而最危险 |
| 4 | 信息不足硬写 | 宁可交一份标清局限的 60 分，不造一份看着完美的 90 分 |
| 5 | 用关键词统计当质量门 | 有序列表都能判错，等于没有门 |
| 6 | 路径写死某一端的 skills 目录 | 换个工具就落错位置，产物加载不到 |
| 7 | 把检查点做成交付阻塞 | 用户要的是产出，不是问卷 |
| 8 | 处理在世非公众人物的私人材料不提示同意 | 涉隐私与本人意愿，须用户提供并自行取得授权 |

## 产出

一个 Skill 交付四件套，缺一件不收：

```
<skill-name>/
├── SKILL.md          # 触发条件、流程、边界、反模式
├── README.md         # 解决什么、什么时候用、内含什么、边界在哪
├── README.en.md      # 与中文版章节一一对应
└── LICENSE           # 与仓库主协议一致
```

调研中间产物（`01` 到 `06`）放在 Skill 目录内的 `references/research/`，随 Skill 一起分发，保证可复核。

新增或修改后同步更新仓库根 `CHANGELOG.md`，中英各一条，写明改了哪个文件、为什么改。
