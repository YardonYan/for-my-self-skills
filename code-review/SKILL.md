# code-review — AI代码七维审查

一句话总纲：审计修复分离——只读、出问题清单（定位+根因+影响+严重度+修复方向）、证据不足不写结论。

## 环境探测（动手前）

1. 确认对象形态：单文件 / 目录 / git diff。范围大于一个模块先拆，按调用链从入口往下，一次一模块
2. 目标文件全文读一遍，禁只看片段——行级问题（泄漏、调试残留）常在上下文之外
3. 判死代码、重复造轮子前必须 Grep 全项目引用：无引用≠死代码（反射/配置/外部脚本调用会骗人）
4. 记录运行环境（OS/语言版本/依赖版本）：跨环境坑的判断基准

## 核心工作流：审计修复分离

「review/看看/审查/诊断」= 只读。产出问题清单后停，等用户确认哪些修，禁顺手改。

清单每条五字段：

- 定位：文件:行号
- 根因：为什么会错（不只说现象）
- 影响面：谁受影响、触发条件
- 维度+严重度：排序按 正确性 > 安全 > 可维护性 > 简单性 > 性能 > 优雅性
- 修复方向：一句话方向，不写实现

证据纪律：

- 验证得动就验证：跑 import、构造最小复现、查官方 API 签名
- 验证不动只标「最可能原因 + 待验证动作」，禁写成结论
- 认定的 bug 证伪一次：构造反例（空值/空集合/单元素/极值/NaN/跨日/停牌）试图推翻，推翻不了才标「已确认」
- 性能建议同理：无 profile/benchmark 前后数字禁说「会变快」，只说「预期」

## 七维检查清单

用户四问的映射：性能→③、冗余→④、bug→①②、产品逻辑→⑥；②⑤⑦为 AI 代码特有补充维度。

### ① 正确性 Bug（用户③）

- 边界反例逐个过：空集合 / None / 单元素 / 0 / 极值 / NaN / 跨日 / 停牌
- 跨环境坑：Windows 路径分隔符、中文编码（文件读写必带 encoding='utf-8'，shell 重定向写中文=GBK 乱码）、时区 naive/aware 混用、CRLF
- 数据口径：日期是序列号（1900/1904 双系统）、百分比文本（"6.67%"）与数值混型、浮点直接 == 比较

### ② AI特有：幻觉与静默降级（人写代码不常有，AI 高发）

- 幻觉 API：参数名/方法签名以官方文档为准，AI「看起来对」≠存在——可疑调用逐个查签名或本地实测
- 静默降级黑名单：except:pass、except:continue、出错返回默认值不标记、错误吞掉继续跑——表面正常，数据已错
- 真要降级：结果必须带质量标记（如〔A/D/E〕），调用方能分辨好坏数据，坏数据不得单独支撑核心结论
- 幻觉配置：引用不存在的配置项/环境变量名，静默拿到默认值跑

### ③ 性能与资源（用户①）

- 大炮打蚊子：循环内 new 对象/拼字符串/做 I/O；循环里逐条查库；可缓存的重复计算（纯函数 lru_cache）
- 泄漏：文件/连接/句柄未关（该用 with）；大文件全量进内存（该流式）；无界拉取列表
- 无护栏：外部调用（API/LLM/TTS/ffmpeg）无超时；重试不幂等、无退避
- 热路径反射/正则；长任务（>3s）占 UI 主线程
- 性能优化建议须给 profile 前后数字，拿不出只说「预期」

### ④ 冗余与一致性（用户②）

- 死代码：全库 Grep 确认无引用才算；注释掉的旧代码=死代码（该删不该注释）
- 调试残留零容忍：breakpoint()/pdb/调试 print（tests 除外）
- 重复：同逻辑 ≥3 处才建议提取（三次法则，≤2 次别提防错误耦合）；同一逻辑两版本并存（改一漏一）优先报
- 重复造轮子：项目已有工具函数/日志方案/样式，又造一个——须全库视角才能发现
- 孤儿 import/变量；_v2/_final/_backup 后缀文件、test/xxx 占位符、随机数字文件名

### ⑤ 安全与泄漏

- 硬编码密钥/token/连接串（应走 os.environ）
- SQL 拼接注入（应参数化查询）
- 日志打印敏感信息（密钥、个人信息）；临时文件留在可预测路径

### ⑥ 产品与过度工程（用户④）

- 删除测试：这功能/这层抽象删掉，用户可感知的行为会坏吗？不会=垃圾功能或过度工程
- 过度工程信号：20 行需求交付三层抽象+配置类+接口预留；BaseController/AbstractManager 空壳基类
- 逻辑优化空间：步骤可合并、if 分支可被数据结构消除（选对结构消分支）、数据没就位却硬凑半成品能跑
- 原则：优先级里性能和优雅性都排在正确性、可维护性之后，别为优雅牺牲别的

### ⑦ 可验证性与可回滚

- 改动无对比基准（改前快照/旧值存档）=盲改
- 关键路径无测试覆盖
- 交付话说「应该能跑/大概修好了」——无证据=未完成

## 能力边界表

| 能力 | 状态 | 说明 |
|---|---|---|
| 只读审查出问题清单 | ✓ | 核心能力 |
| 顺手修复/顺手重构 | ✗ 高危 | 审计修复分离，清单确认后才动手 |
| 修复实施 | 走正常编码流程 | 本 skill 清单当定位输入；批量改动（≥3文件）先试点 2-3 处 |
| 性能调优实施 | ✗ | 只报方向和基线要求，不代跑 |
| 渗透测试/专业安全审计 | ✗ | 只扫常见泄漏模式 |

## FAQ / 故障剧本

- 误报多 → bug 条目列出前先跑验证或明确标「待验证」；静态看不出的禁写成结论
- 大仓库范围炸 → 按 import 依赖分层，入口/核心路径优先，一次一模块，禁一次全库
- AI 代码「看起来对」但跑不通 → 查官方文档签名，或本地 `python -c "import ..."` 实测，别信代码外观
- 用户看完清单说「修」→ 切正常编码流程，先复现再修，修完逐条对照清单确认
- 分不清风格问题还是真问题 → 过「删了会坏什么」测试：不坏=低优先级或不报
- 清单要不要落文件 → 默认对话内输出；用户明说要文档才写 md，禁主动生成
- 同一处看不出来两次结果不一样 → 说明证据不足，回到验证动作，禁凭印象二选一

## 自检清单（交付前）

□ 每条问题带文件:行号
□ bug 类条目有验证证据或明确标「待验证」
□ 严重度按 正确性>安全>可维护性>简单性>性能>优雅性 排序
□ 全程零改动（git status 干净，或未用任何写工具碰目标文件）
□ 用户四问覆盖：性能③、冗余④、bug①②、产品⑥
□ 可疑 API 签名逐个查过
□ 无「顺手改进」夹带（无关死代码只提示不删）
