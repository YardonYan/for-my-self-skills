# code-review — AI 生成代码的七维审查

> 审计与修复分离：review 只读，出问题清单，不动手改。

## 解决什么

AI 写的代码有几类人写代码不常有的病，而且从代码外观上看不出来：

- 调用了不存在的 API（幻觉），参数名看着对，实际没这个签名
- `except: pass` 吞掉错误悄悄给默认值（静默降级），表面正常，数据已经错了
- 20 行需求交付三层抽象、空壳基类（过度工程）
- 项目里已有轮子又造一个（重复造轮子），只有全库视角才看得见

外加人写代码也会犯的老毛病：死代码、调试残留、没关的句柄、无超时的外部调用、无对比基准的盲改。

这个 Skill 用七维清单逐条扫，每条问题必须带定位行号、根因、影响面和修复方向，证据不足的只标「待验证」，不写成结论。

## 什么时候用

```
用 code-review 审查这段代码，只出问题清单不要改。
交付前用 code-review 做一次七维自检。
这段代码是 AI 生成的，重点扫幻觉 API 和静默降级。
```

## 七维清单

| # | 维度 | 扫什么 |
|---|---|---|
| ① | 正确性 Bug | 边界反例（空 / None / 单元素 / 极值 / NaN / 跨日）、Windows 路径分隔符、中文编码 GBK 乱码、时区 naive/aware 混用、数据口径 |
| ② | 幻觉与静默降级 | 幻觉 API 签名、`except: pass` 黑名单、无质量标记的降级、引用不存在的配置项 |
| ③ | 性能与资源 | 循环内 new / 拼字符串 / 做 I/O、句柄未关、大文件全量进内存、外部调用无超时、无 profile 数字的「变快了」 |
| ④ | 冗余与一致性 | 死代码（须全库 Grep 确认）、调试残留、同逻辑 ≥3 处才建议提取、重复造轮子、`_v2` / `_final` 后缀文件 |
| ⑤ | 安全与泄漏 | 硬编码密钥、SQL 拼接注入、日志打印敏感信息 |
| ⑥ | 产品与过度工程 | 删除测试（删掉会不会坏）、空壳基类、数据没就位硬凑半成品 |
| ⑦ | 可验证性与可回滚 | 无对比基准的盲改、关键路径无测试、「应该能跑」式交付 |

严重度排序铁律：**正确性 > 安全 > 可维护性 > 简单性 > 性能 > 优雅性**。

## 工作流

1. 环境探测：目标文件全文读一遍（禁只看片段）、Grep 全项目引用、记录运行环境
2. 七维逐条扫描，可疑 API 查官方签名或本地实测
3. 认定的 bug 证伪一次：构造反例（空值 / 空集合 / 极值 / NaN / 跨日）试图推翻自己，推翻不了才标「已确认」
4. 输出问题清单，**停在这里**，等用户确认要修哪几条
5. 用户确认后切正常编码流程修复——修复不是这个 Skill 的职责

## 边界

| 能力 | 状态 |
|---|---|
| 只读审查出问题清单 | ✓ 核心能力 |
| 顺手修复、顺手重构 | ✗ 高危，审计修复分离 |
| 性能调优代跑 | ✗ 只报方向和基线要求 |
| 渗透测试、专业安全审计 | ✗ 只扫常见泄漏模式 |
