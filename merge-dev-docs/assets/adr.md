# ADR 模板

> 一个真冲突一条，文件名 `NNNN-<kebab-主题>.md`，放 `docs/adr/`。
> 编号递增不复用。已被取代的 ADR 改状态、不删文件。

```markdown
# NNNN. <决定了什么，一句话>

日期：YYYY-MM-DD
状态：已采纳 ｜ 取代：NNNN-xxx ｜ 已被取代：NNNN-yyy
来源：合并 `<文件夹A>` 与 `<文件夹B>` 时的冲突 #<矩阵行号>
裁决层级：代码可查 ／ 仅决策理由 ／ 人工确认

## 背景

两套文档在同一问题上给了不同规定，必须择一，否则读者不知道该执行哪条。

- A（`<路径>` L<行>，claim A/<文档>.md:n，**已落地**）：<原文主张，引用原话，不要转述成模糊说法>
- B（`<路径>` L<行>，claim B/<文档>.m，**待实施**）：<原文主张>

不合的是四元式中的 `<对象/动作/阈值/例外>` 项。

<!-- 时态不同则本条不成立，改为合成一句含时序的话，不出 ADR -->

## 证据

按优先级列出实际查证过程，**不接受**「B 写得更详细」「A 更新」「A 团队更规范」这类无取证判断。

### 有代码库时

1. 线上实现：`<grep / 统计命令>` → `<结果，含数量>`
2. 历史事故或评审争论：`<issue / commit / PR 编号>` → `<结论>`
3. 时间意图：A 最后修改 <日期>，B 最后修改 <日期>（仅在前两条无证据时启用）

### 无代码库时

1. 决策理由在位的一方：`<引用 A/文档.md:n 的原话>` → `<该理由是否覆盖 B 的关切>`
2. 另一方是否有理由：`<有则引用，无则写「未展开」>`
3. 双方论证都站得住 → 转人工确认，填下面的「人工确认」块

## 决定

<采纳的规则，写成一条可执行、有具体名字、带反例的话。这条话就是最终进合并稿的内容，两边必须一字不差。>

## 人工确认（无代码证据且双方都有理由时必填）

| 项 | 内容 |
|---|---|
| A 的论证 | <...> |
| B 的论证 | <...> |
| 分歧的本质 | <是权衡不同，还是其中一方漏想了某个约束> |
| 需要谁定夺 | <姓名/角色> |
| 确认结论 | <日期> <结论> |
| 是否推翻原建议 | 是／否。若是，理由：<...> |

**用户或同事推翻建议时，本栏是必填项。** 理由要回填进下面的「什么情况会推翻这个决定」。

## 被否掉的一方怎么说

保留原文主张与出处，不删。作者需要看到自己的意见被记录而非无视——这是合并能否真正落地的关键，比裁决正确与否更容易被忽略。

## 代价

- 需要改动：<工作量、涉及文件数>
- 谁可能不同意：<角色>
- 过渡期怎么过：<双写 / 兼容 / 分批>

## 什么情况会推翻这个决定

必须写得出具体条件。写不出来说明当初不是决策而是随手选择。

- 可观测条件：<如"新接口数量超过 50 个且 60% 由另一套生成器产出">
- 检查时机：<每季度 / 下次架构评审>
- 推翻后的动作：<回到 B 方案 / 引入 X>

## 复核人

<姓名> — 需要他在合并稿定稿前确认，否则视为未裁决。
```
