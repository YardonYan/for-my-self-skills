# Judgment Rules

合并时的判定细则。Phase 3-4 遇到不确定就回这里查。

## 一、先判时态，再谈冲突

架构文档合并的头号杀手是时态混用：两套文档一套写着旧设计、一套写着新方案，直接合并会把已废弃的架构当成现状，读者照着建就炸。

**每条 claim 在进入冲突矩阵前必须先标时态标签。** 脚本的 temporal signal 只是候选行，标签要回原文确认。

| 标签 | 判据 | 处理 |
|---|---|---|
| 已落地 | 描述当前系统实际状态；或带现状类标记（现状/目前/已上线/现已） | 参与裁决 |
| 已废弃 | 带废弃类标记（废弃/下线/不再使用/历史遗留/已废弃） | **不进正文**，进淘汰区清单 |
| 待实施 | 带未来类标记（规划/计划/将来/下一步/待实施/拟/roadmap） | 可进正文但必须标 `[待实施]`，且不与已落地规则混写 |

三条配套规则：

1. **已被取代的旧方案要写清被谁取代。** 「一主两备 → 多活三节点」这类，必须在正文留下替代关系，否则读者看到旧文档会以为还有两套方案在用。
2. **两套文档时态不同不构成冲突。** 一边写现状、一边写规划，是对同一主题的不同时间切片，正确处理是合并成一句含时序的话：「当前 X，规划 Y 时切换到 Z」。不要按冲突裁决。
3. **待实施项要能追溯到决策。** 孤立的「计划做 X」没有决策依据，进淘汰区或写成待确认项，不进正文——否则半年后没人知道它还作不作数。

脚本的正则只标候选。像「这一节是对旧拓扑的替换」这种句子没有关键词，靠读。

## 二、把规则压成四元式再比较

自然语言表述不同，读起来像冲突；也像不冲突。先做形式化，每条规则拆成四项：

| 项 | 含义 | 例 |
|---|---|---|
| 对象 | 约束的是什么东西 | 迁移文件 |
| 动作 | 要求 / 禁止 / 建议 | 要求命名格式 |
| 阈值 | 具体数值、路径、名字 | `<序号>_<描述>.sql` |
| 例外 | 什么情况下不适用 | 无 |

四元式比较结果决定分类：

- **四项全同，措辞不同** → 等价。保留阈值更具体的一条，删另一条。
- **对象同、动作同、阈值互补** → 互补。合成一条完整规则。
- **对象同、动作矛盾（一禁一允），或阈值不同** → 真冲突。进第四节。
- **对象不同但属于同一流程** → 互补，合并到同一章节下相邻排列。
- **一方写了另一方没写** → 单边条目，过第五节门槛。

**架构层要用更粗的四元式。** 组件划分、部署拓扑、技术选型的「对象」是系统整体而非单条规则，比较时看的是整节的立场，不能按行拆。判据是读完两边整节，问「这两节描述的是同一个系统在同一时刻的不同方案，还是同一方案的不同侧面」。

## 三、真冲突的三种可自动化解情形

有些看起来是冲突，其实不用人介入，先检查这三种：

1. **阈值可叠加。** A：「业务回填禁止写在迁移里」；B：「小于 1000 行的回填可直接写在迁移里」。合成为：「回填默认独立任务分批跑；单批 < 1000 行可写在迁移内，需附回滚语句」。**这是合并最常见的收益点**：一份只写原则，另一份只写例外，合起来才是完整规则。
2. **粒度可层级。** A 粗（「错误统一处理」）、B 细（「错误码登记在 `docs/error-codes.md`，禁止透出内部异常」）。粗的降级为 B 的章节标题，不进正文当独立规则。
3. **作用域不同。** 两条看似矛盾，实际各适用于不同子系统。合成为带条件的一条，正文写明条件。**先确认是真不同作用域，还是在掩盖分歧**——判据是两边描述的适用范围是否真的可区分。

## 四、无代码证据时的裁决路径

有代码库时证据优先级很清楚，按序取证：

1. **线上实现事实** — grep 统计哪种写法占多数。占 80% 以上的一方胜出，另一方是待清理债务而非规范。
2. **事故与评审记录** — git log / issue / PR 评论里同一问题是否反复出现。
3. **近期作者的意图** — 较新的文档更可能反映当前判断。

**没有代码库可查时，上面三条全部失效。** 此时按以下顺序处理，不要退回到「哪边写得好」：

1. **先查画像里有没有决策理由。** Phase 2 的独立画像若显示一方有明确权衡论证（为什么选 X 放弃了 Y），该论证本身就是证据等级较高的材料。若另一方对该点完全没有表态，那不是冲突，是一方单方忽略了这个问题——按有论证的一方走，同时把缺失理由记为该方待补。
2. **一方有论证、一方无理由或理由薄弱** → 采有论证方，并记录理由。
3. **双方都有明确论证且都站得住** → 真裁决不了，输出 `待裁决`，把两方论证完整列出，注明这需要人来定，并给出「定夺前临时按哪一方执行」的选择（选改动成本更低的一方）。
4. **双方都没论证** → `待裁决`，且必须指出这是双方共同的文档缺口。

**硬禁用的裁决依据**（缺证据时尤其容易滑进去）：

- 作者职级
- **作者所属团队或部门立场**——同事之间的文档合并里，「我们部门一直这么做」压过「他们部门那么写」是最常见的失控点。它不构成技术证据
- 文档篇幅、详细程度
- 模型的语言流畅度偏好、「看起来更专业」
- 文档写得更晚（`近期作者意图` 只在前两档有证据时才作为辅助，不单独定胜负）

架构层的组件划分、部署拓扑、技术选型三类冲突，**即使无代码可查也不允许留模糊表述**。文档写「用 PostgreSQL」而实际是 MySQL，读者照着建库就炸。无证据时写「待确认：<两方方案>，需 XX 角色在评审会定夺」，不要写成看似确定的单一方案。

## 五、留下门槛（判断「优点」）

单边条目要过三条检查才留下：

- **可执行**：照着这句话就能做出一个动作。
- **有名字**：含具体路径、命令、命名模式、数值阈值之一。
- **有反面**：能说出违反它会怎样（出错、评审打回、线上事故）。

三条满足两条以上留，否则丢。

**文档变薄是合并的正常结果。** 如果合并稿比两套原文加起来还长，几乎一定是把冗余也合并了。

架构文档另有一条门槛：**组件图、类图、字段清单一律不写正文**，改成指向源码路径或设计稿链接。这类内容合并当天就过期。

## 六、中文文档特有的坑

- **同一概念不同中文词**：「服务」「模块」「组件」在多套文档里可能指同一层，也可能不是。给每个术语定一个英文标识符，中文只作显示名。
- **同一中文词指不同东西**：「订单」= 交易单 / 出库单 / 报价单。必须建术语表，写明「不是什么」。这是企业文档合并里最贵的错——措辞统一了，语义反而糊掉了。
- **标点与全半角**：合并稿统一一次，否则 diff 噪音掩盖真实改动。
- **「必须/应当/可以」混用**：统一到三档：**必须**（违反阻断合入）/ **默认**（可评审后例外）/ **可选**，并在文档头写明三档含义。

## 七、术语对齐表是强制产物

每个术语四列：`中文名 | 英文标识符 | 定义（一句话） | 不是什么`

来源：SAME TOPIC 与 RELATED 的所有条目。**两边对同一词给了不同定义的，是真冲突，按第四节裁决**。

术语表放开发规范分册，架构分册引用它。

## 八、多于两套文档

顺序合并会偏袒第一个基底。做法：

1. 选**内容最全**的那套为基底（不是最新也不是最详细）。
2. 其余各套逐一与基底 `compare`，每轮产出一份冲突矩阵。
3. 全部裁决完再统一重写一遍，不要在逐轮增量中定稿——每轮的表述都会被上一轮的措辞锁住。
4. 三个以上来源时，一条规则的出处必须全部列出。

## 九、失败模式

- **平均化**：把两条规则合并成一句模糊上位词。症状：合并稿里出现「应合理选择」「视情况而定」。
- **两边都留**：用「或」连接冲突规则，读者无法执行。
- **静默取舍**：删了一方的内容但不写 ADR，作者会认为被无视，然后重新加回去。
- **只重排不合并**：产出一个两部分目录，前一半是我的、后一半是他的。这是失败的合并，比原文档更糟。
- **时态混淆**：把已废弃设计写成现状，或把规划写成既定事实。**架构文档里这一条比上面五条都致命。**
- **污染式比较**：先看 A 再看 B 导致 B 被 A 的框架重塑，冲突矩阵失真。表现为假冲突多、漏冲突多。
- **跨文件夹逐篇对撞**：文件夹内部就自相矛盾时，不先内部对齐会把矛盾放大。Phase 1 先做内部体检。
- **把代码事实抄进文档**：字段清单、类图在合并当天就过期。改成指向源码路径。
- **硬闸被跳过**：矩阵还没被过目就写完合并稿，用户失去复核入口。

## 十、自检清单（交付前逐条过）

- [ ] 每条规则都能回答「违反它会怎样」
- [ ] 没有出现「或」连接的冲突规则
- [ ] 每个真冲突都有 ADR，每条 ADR 都有「什么情况推翻它」
- [ ] 所有 `待裁决` 项都指名了负责人
- [ ] 所有 claim 都标过时态标签；已废弃项都在淘汰区清单里，且写明被谁取代
- [ ] 待实施项都标了 `[待实施]`，且没有与已落地规则混写
- [ ] 术语表覆盖了所有 SAME TOPIC 条目
- [ ] 架构层无代码可查的冲突全部写成「待确认」而非看似确定的单一方案
- [ ] 合并稿长度 ≤ 两套原文总长的 70%（超出则检查是否保留了冗余）
- [ ] 文中引用的每个文件路径真实存在
- [ ] 架构分册与开发规范分册没有互相复述，指向而非重写
- [ ] 文档头有 `最后核对：YYYY-MM-DD`
